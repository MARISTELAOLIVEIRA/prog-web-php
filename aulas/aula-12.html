Banco de Dados: modelagem e tabelas com SQLite

A planilha bagunçada da loja vira três tabelas ligadas por chaves: clientes, produtos e pedidos.

Objetivo do dia

Modelar o banco da loja (clientes, produtos e pedidos), identificar as chaves primárias e estrangeiras e criar as tabelas no SQLite, o mesmo banco do Cadastro de Clientes.

Competência

Modelar e implementar bancos de dados para aplicações web. Situação de Aprendizagem 2: persistência de dados e programação orientada a objetos.

Antes da aula

Deixar a versão 3 do Cadastro de Clientes (aula 11) rodando com o php -S ou com o XAMPP.

P1 · o problema

A planilha que repete tudo

A loja de artesanato controla os pedidos numa planilha. Cada linha é um pedido, e em cada linha vão de novo o nome, o telefone e o e-mail da cliente, o nome e o preço do produto. A Ana comprou três vezes: o nome dela foi digitado três vezes, cada vez de um jeito.

Onde os sistemas guardam as informações sem repetir tudo? Hoje a planilha vira um banco de dados relacional: cada coisa na sua tabela, e as tabelas ligadas por chaves.

C1–C6 · conceitos

Da planilha ao banco, em seis peças

C1

Cada coisa na sua tabela

Na planilha, a cliente, o produto e o pedido estão todos na mesma linha. No banco relacional, cada coisa do mundo real ganha a sua tabela: uma para clientes, uma para produtos, uma para pedidos.

A Ana fica escrita uma vez só. Se ela trocar de telefone, muda uma linha, e não trinta.

1-- a planilha: tudo junto, e a Ana se repete2data  | cliente   | telefone        | produto | preço303/10 | Ana Souza | (61) 99599-3513 | Caneca  | 35,90405/10 | ana souza | 61 99599 3513   | Vaso    | 59,0056-- o banco: cada coisa na sua tabela7clientes: id, nome, email, telefone8produtos: id, nome, preco9pedidos:  id, cliente_id, produto_id, quantidade, data
C2

Tabela, coluna, linha e tipo

A tabela é a gaveta; cada coluna é um dado (nome, preço) e cada linha é um registro (um produto).

Cada coluna tem um tipo. No SQLite são poucos: INTEGER (número inteiro), REAL (número com vírgula) e TEXT (texto e datas). NOT NULL obriga a preencher; UNIQUE não deixa repetir; CHECK confere uma regra.

1CREATE TABLE IF NOT EXISTS produtos (2    id INTEGER PRIMARY KEY AUTOINCREMENT,3    nome TEXT NOT NULL UNIQUE,         -- não repete4    preco REAL NOT NULL CHECK (preco >= 0)   -- sem preço negativo5)
C3

Chave primária: o RG da linha

A chave primária (PK, de primary key) identifica cada linha sem confusão. Nome não serve: existem duas "Ana Souza". O id serve: é único e nunca muda.

Com AUTOINCREMENT, o próprio banco dá o número: 1, 2, 3... Você nunca escreve o id no INSERT.

1-- o id não aparece no INSERT: o banco numera2INSERT INTO produtos (nome, preco) VALUES ('Caneca', 35.90);   -- id 13INSERT INTO produtos (nome, preco) VALUES ('Vaso', 59.00);     -- id 2
C4

Chave estrangeira: a ponte entre as tabelas

O pedido não guarda o nome da cliente: guarda o número dela, o cliente_id. Essa coluna é uma chave estrangeira (FK, de foreign key): aponta para o id de outra tabela.

O banco confere a ponte: pedido de cliente que não existe é recusado.

Pegadinha do SQLite: a conferência das chaves estrangeiras vem desligada. Liga com PRAGMA foreign_keys = ON, toda vez que conecta.

1CREATE TABLE IF NOT EXISTS pedidos (2    id INTEGER PRIMARY KEY AUTOINCREMENT,3    cliente_id INTEGER NOT NULL,   -- o número da cliente4    produto_id INTEGER NOT NULL,   -- o número do produto5    quantidade INTEGER NOT NULL,6    FOREIGN KEY (cliente_id) REFERENCES clientes (id),7    FOREIGN KEY (produto_id) REFERENCES produtos (id)8)
C5

Um para muitos: o diagrama

Uma cliente faz muitos pedidos; cada pedido é de uma cliente. Isso é um relacionamento um para muitos (1:N). O mesmo vale para produto e pedido.

O diagrama entidade-relacionamento (DER) desenha isso antes do código: as tabelas, as colunas, as chaves e as linhas que ligam. É a planta da casa antes do tijolo.

clientes

  • PK id
  • nome
  • email
  • telefone
1N

pedidos

  • PK id
  • FK cliente_id
  • FK produto_id
  • quantidade
  • data
N1

produtos

  • PK id
  • nome
  • preco
C6

SQLite: o banco é um arquivo

O SQLite não tem servidor para ligar: o banco inteiro é um arquivo, o loja.sqlite, e o PHP já vem com ele. Renomear o banco é renomear o arquivo; a cópia de segurança é copiar o arquivo.

Na aula 14, o mesmo banco vai para o MySQL do XAMPP, um servidor de banco de dados. As tabelas e o SQL quase não mudam; muda a conexão.

Lembrete: o arquivo do banco fica no .gitignore. Dado de cliente não vai para o GitHub.

1// o banco é este arquivo; se ele não existe, o PHP cria2$pdo = new PDO('sqlite:' . __DIR__ . '/loja.sqlite');34// liga a conferência das chaves estrangeiras5$pdo->exec('PRAGMA foreign_keys = ON');67// na aula 14, só esta linha muda:8// new PDO('mysql:host=localhost;dbname=loja;charset=utf8mb4', 'root', '')
T1 · tutorial

Mão na massa: o banco da loja em 4 passos

Primeiro o desenho, depois o código, depois a prova. Faça um passo de cada vez: copie, rode, teste, entenda e só depois passe para o próximo.

O combinado de hoje: os passos 1 a 3 na aula. O passo 4 (DB Browser for SQLite) é para quem terminar antes ou para casa, se o laboratório não tiver o programa.

Antes de começar

O ponto de partida é a versão 3 da aula 11

  1. Abra a pasta cadastro-clientes no VS Code. Não terminou a versão 3? Copie da aula 11.
  2. Ligue o servidor no terminal do VS Code: php -S localhost:8000. No laboratório: C:\xampp\php\php.exe -S localhost:8000. Prefere o XAMPP? Deixe a pasta dentro do htdocs e ligue o Apache; o endereço fica http://localhost/cadastro-clientes/.
  3. Confira se http://localhost:8000/cadastro.php abre e cadastra.
  4. Rode git status: tem que aparecer "nothing to commit". Se aparecer arquivo mudado, faça o commit antes de começar.

Como copiar: clique na aba do arquivo, depois em Copiar. No VS Code, apague tudo o que tinha no arquivo (Ctrl + A e Delete), cole (Ctrl + V) e salve. A etiqueta de cada aba avisa: novo (crie o arquivo), mudou (troque o conteúdo todo) ou igual (não precisa mexer).

Passo 1

O desenho: o diagrama do banco no draw.io

Antes de escrever SQL, o banco é desenhado. Errar no desenho custa uma borracha; errar no banco com dados dentro custa caro.

Faça assim:

  1. Abra o draw.io (app.diagrams.net) no navegador. Na primeira tela, escolha salvar no Dispositivo e crie um diagrama em branco.
  2. No painel da esquerda, digite table na busca de formas (ou, em + Mais formas, ligue a categoria Entity Relation). Arraste a forma de tabela três vezes para a folha.
  3. Dê dois cliques no título de cada uma e escreva clientes, produtos e pedidos.
  4. Escreva as colunas como no diagrama da C5. Marque PK no id de cada tabela e FK no cliente_id e no produto_id.
  5. Passe o mouse em pedidos, puxe a setinha azul até clientes e depois até produtos. Clique na linha e, no painel da direita, escolha a ponta de muitos (o "pé de galinha") do lado de pedidos.
  6. Salve: Arquivo › Exportar como › PNG, marque a opção de incluir uma cópia do diagrama e salve como diagrama-loja.drawio.png dentro da pasta cadastro-clientes. Esse PNG abre como imagem no GitHub e continua editável no draw.io.

Teste: confira o seu diagrama com estas perguntas.

  1. O nome da cliente aparece em uma tabela só? (Tem que aparecer só em clientes.)
  2. Se a Ana trocar de telefone, quantas linhas mudam? (Uma.)
  3. Dá para saber quem fez o pedido 7 olhando só a tabela pedidos? (Dá o número, o cliente_id; o nome está em clientes.)
  4. O preço do produto está em pedidos? Se estiver, ele vai se repetir: tire.
Agora é com você:
  • Acrescente a coluna estoque em produtos. Que tipo ela tem?
  • A loja quer saber a cidade de cada cliente. Em que tabela entra a coluna cidade?
  • Pense: e se um pedido tiver vários produtos? Anote a ideia; ela volta no desafio extra.

Pronto o desenho? Guarde e envie para o GitHub, um comando de cada vez:

1# 📦 1. põe na caixa2git add .3# 🏷️ 2. fecha e etiqueta4git commit -m "Passo 1: diagrama do banco da loja"5# 🚚 3. envia6git push

O git push reclamou? Se aparecer rejected, rode git pull e depois git push de novo. Se aparecer no upstream branch, rode uma vez git push -u origin main.

Passo 2

O código: as três tabelas nascem no banco.php

O desenho vira SQL. O banco.php passa a criar as tabelas produtos e pedidos, com as chaves estrangeiras, e o banco ganha o nome da loja.

Faça assim:

  1. Desligue o servidor (Ctrl + C no terminal).
  2. No VS Code, clique com o botão direito no clientes.sqlite, escolha Renomear e troque para loja.sqlite. O banco é um arquivo: renomeou o arquivo, renomeou o banco. Os clientes cadastrados continuam lá dentro.
  3. Troque o conteúdo do banco.php (etiqueta mudou) e do .gitignore (agora com *.sqlite, que vale para qualquer banco).
  4. Crie o teste-banco.php (etiqueta novo): é o raio-x do banco.
  5. Ligue o servidor de novo e abra http://localhost:8000/teste-banco.php: aparecem as 3 tabelas, com PK e FK. Compare com o seu diagrama.
  6. Abra http://localhost:8000/cadastro.php e cadastre alguém: tudo continua funcionando, sem mudar o clientes.php.

Teste:

  1. Rode git status: o loja.sqlite não pode aparecer. Se aparecer, confira o .gitignore.
  2. No banco.php, apague o IF NOT EXISTS da tabela produtos e recarregue. O erro table produtos already exists aparece: a tabela já foi criada na primeira vez. Ponha o IF NOT EXISTS de volta.
  3. Cadastre de novo um e-mail que já existe: o aviso de e-mail repetido continua funcionando.
Agora é com você:
  • Ponha a coluna estoque INTEGER NOT NULL DEFAULT 0 na tabela produtos. Recarregou e ela não apareceu? O CREATE TABLE IF NOT EXISTS não mexe em tabela que já existe. Desligue o servidor, apague o loja.sqlite (só tem dado de teste) e ligue de novo.
  • No raio-x, mostre também o total de tabelas em letras grandes, com um <h2>.

Funcionou? Guarde e envie para o GitHub, um comando de cada vez:

1# 📦 1. põe na caixa2git add .3# 🏷️ 2. fecha e etiqueta4git commit -m "Passo 2: tabelas produtos e pedidos"5# 🚚 3. envia6git push
Passo 3

A prova: a chave estrangeira em ação

Um teste que cadastra produtos e um pedido certo e, de propósito, tenta um pedido de um cliente que não existe. Se a chave estrangeira estiver ligada, o banco recusa.

Faça assim:

  1. Crie o teste-chaves.php (etiqueta novo), cole e salve.
  2. Abra http://localhost:8000/teste-chaves.php e leia as cinco linhas, com calma.
  3. A linha 4 tem que dizer FOREIGN KEY constraint failed: o banco recusou o pedido do cliente 999.
  4. Abra o teste-banco.php de novo: agora produtos tem 3 linhas e pedidos, 1.

Teste (erros de propósito):

  1. No banco.php, ponha // na frente da linha do PRAGMA foreign_keys = ON, salve e recarregue o teste-chaves.php. Agora aparece "Opa! O banco aceitou um pedido do cliente 999": sem o PRAGMA, o SQLite não confere nada. Tire o // e salve. (O pedido errado ficou na tabela: no passo 4 você vai achar e apagar.)
  2. Recarregue o teste-chaves.php três vezes e olhe o raio-x: os pedidos aumentam, os produtos não. Por quê? (Dica: UNIQUE e INSERT OR IGNORE.)
  3. No pedido certo, troque ':quantidade' => 2 por 0 e recarregue: o CHECK (quantidade > 0) barra com CHECK constraint failed. Volte para 2.
Agora é com você:
  • Acrescente um pedido do produto 999, dentro de outro try e catch. O banco recusa também?
  • Cadastre um quarto produto da loja no foreach.
  • Tente cadastrar um produto com preço -5. Quem barra?

Funcionou? Guarde e envie para o GitHub, um comando de cada vez:

Passo 4

Olhando por dentro: o DB Browser for SQLite

O DB Browser for SQLite abre o loja.sqlite como uma planilha: dá para ver a estrutura, os dados e cadastrar à mão, conferindo o que o PHP gravou.

Faça assim:

  1. Baixe em sqlitebrowser.org. No Windows do laboratório, a versão .zip (no installer) roda sem instalar. No Mac, baixe o .dmg.
  2. Clique em Abrir banco de dados e escolha o loja.sqlite, na pasta cadastro-clientes.
  3. Na aba Estrutura do banco de dados, abra as três tabelas e compare com o seu diagrama.
  4. Na aba Executar SQL, digite PRAGMA foreign_key_check; e clique no ▶. Aparece o pedido "órfão" do cliente 999, que entrou no teste do passo 3 com o PRAGMA desligado.
  5. Na aba Navegar dados, escolha a tabela pedidos, clique na linha do cliente 999 e em Excluir registro. Rode o PRAGMA foreign_key_check; de novo: agora não aparece nada.
  6. Ainda em Navegar dados, escolha produtos, clique em Novo registro e cadastre um produto (deixe o id em branco: o banco numera).
  7. Clique em Escrever modificações (Ctrl + S). Sem isso, nada é gravado e o PHP pode dar database is locked.

Sem o DB Browser? No VS Code, a extensão SQLite Viewer abre o loja.sqlite com dois cliques, só para ver. Para cadastrar, use o teste-chaves.php.

Teste:

  1. Abra o teste-banco.php: o produto que você cadastrou à mão entrou na contagem.
  2. No DB Browser, em pedidos, troque o cliente_id de um pedido para 999 e tente gravar. O DB Browser liga a conferência das chaves sozinho e recusa. Cancele a mudança.
  3. Rode git status: o loja.sqlite continua de fora.
Agora é com você:
  • Pelo DB Browser, cadastre 3 pedidos para clientes diferentes.
  • Conte à mão: quantos pedidos cada cliente tem? Na aula 13, o SQL faz essa conta numa linha.

Tudo certo? Guarde e envie para o GitHub, um comando de cada vez:

A planilha que não fechava

Caso fictício, criado para a aula.

Uma loja de artesanato controlava os pedidos numa planilha. O nome e o telefone da cliente se repetiam em cada pedido. Quando uma cliente trocou de telefone, metade das linhas ficou com o número novo e metade com o antigo, e a loja ligou para o número errado na entrega.

Para discutir em grupo

  2. Como separar em tabelas?
  3. Que coluna liga o pedido à cliente?

S1 · conexão STEAM

Toda peça tem um código

E

Eletrônica

Na placa, cada peça tem um código único: R1, R2, C3. Esse é o id. E a lista de ligações diz qual pino vai em qual: é a chave estrangeira, apontando de uma peça para outra.

M

Matemática

O nome "relacional" vem da matemática: em 1970, Edgar F. Codd, da IBM, propôs guardar os dados como relações, os conjuntos de pares e trincas que você vê na escola. Cada tabela é uma relação.

A

Arte

No ateliê de sucata, ninguém joga tudo numa caixa só: parafusos numa gaveta, fios em outra, e cada gaveta com etiqueta. Organizar o banco é organizar o ateliê.

D1 · desafio extra

Terminou antes? Tem mais.

Hoje cada pedido tem um produto só. Na vida real, um pedido tem vários. Crie a tabela itens_pedido, com pedido_id, produto_id e quantidade, as duas chaves estrangeiras, e desenhe no diagrama. Isso é um relacionamento muitos para muitos (N:N): um pedido tem muitos produtos, e um produto está em muitos pedidos.
